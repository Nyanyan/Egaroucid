# FlipSightボット接続

Egaroucid for ConsoleをFlipSightのボット対局APIに直接接続します。対応種目は標準の8×8オセロ（std）です。FlipSightのボット管理画面でも、対応ゲームを「標準」だけに設定してください。

API v2に対応しています。接続直後の `state` と、その後の `match` イベントで状態を受け取り、`agent_poll` は呼びません。公式仕様では `agent_poll` は2026年11月22日0時（日本時間）に廃止されます。旧オプション `-flipsightnostream` は使用できず、指定するとエラーで終了します。

## ビルド

CMakeでは `INCLUDE_FLIPSIGHT` を有効にします。既定値はOFFです。

```powershell
cmake -S . -B build/flipsight -DINCLUDE_FLIPSIGHT=ON
cmake --build build/flipsight --config Release
```

Windowsは標準のWinHTTPを使います。Linux・macOSではlibcurlの開発用ヘッダーとライブラリが必要です。コンパイラーを直接呼ぶ場合は `INCLUDE_FLIPSIGHT` を定義し、Windowsでは `winhttp`、Linux・macOSでは `curl` をリンクしてください。

既存のVisual Studioプロジェクトでも有効にできます。

```powershell
msbuild Egaroucid_for_Console.vcxproj /p:Configuration=SIMD /p:Platform=x64 /p:IncludeFlipSight=true
```

GGSとFlipSightは同じ実行ファイルに組み込めます。起動時にはどちらか一つの接続モードを選んでください。

## 起動

CMakeでビルドしたコンソール版は、Release構成でも `bin/` 直下に出力します。このリポジトリの `bin/resources/` にある評価ファイルと定石ブックを、そのまま読み込みます。評価ファイルは `eval.egev2` と `eval_move_ordering_end.egev`、定石ブックは `book.egbk3` です。以下はWindowsのCMakeビルドを、リポジトリ直下から起動する例です。`<token>` をFlipSightで発行したボット用トークンに置き換えます。

```powershell
.\bin\Egaroucid_for_Console.out.exe -flipsight "<token>" -fsthread 4 -hash 25
```

実行ファイルを別の場所へ配置する場合は、その隣に `resources/` を配置してください。

`-fsthread M` は、サイトへ報告する盤面あたりのスレッド数です。APIの上限に合わせ、Mは1〜4、省略時は4です。起動時の確保数や、同時対局の増加に応じた増員は従来どおりです。

`-level` を省略すると、FlipSightから受け取った残り時間に合わせて探索します。レベルを指定する場合は、同じコマンドに `-level 3` などを追加します。指定できるレベルは0〜60です。指定レベルの探索は、残り時間から通信の余裕を差し引いた時間を上限に実行します。定石ブックを使わず、指定レベルの探索だけで着手を選ぶ場合は `-nobook` も追加してください。

初期化後に対局の待ち受けを始め、対応する申し込みを自動で承諾します。Ctrl+Cで通信・探索・ponderを停止して終了します。

| 引数 | 動作 |
| --- | --- |
| `-flipsight <token>` | ボット用トークンを渡して接続する |
| `-fsthread M` | サイトへ盤面あたりMスレッドと報告する。起動時は2Mスレッドを確保し、対局の追加に応じて増員する（既定値4） |
| `-level N` | 指定レベルで探索する。省略時は残り時間に合わせる |
| `-flipsightnoponder` | 相手の手番中の先読みを無効にする |
| `-flipsightnostream` | API v2では使用不可。指定するとエラーで終了する |
| `-flipsightapi <https_url>` | 接続するAPIのURLを変更する |
| `-fslogfile <file>` | FlipSightのログファイルを指定する。`-fslogdir`より優先する |
| `-fslogdir <directory>` | FlipSightのログ保存先ディレクトリを指定する |

## ログ

FlipSightモードでは、`-noise`を付けなくても、起動・接続状況、着手と着手後の残り時間、および各盤面の評価値・探索深さを標準出力へ表示します。各盤面の評価値の合計も表示します。評価値はボット側から見た石差です。盤面が終了したら、その盤面の表示を最終石差へ更新し、合計も更新します。サイトから対局全体の確定石差を取得できた場合は、合計欄にその値を使います。エラーと再接続時の案内は標準エラー出力へ表示します。

局面更新、探索開始、API呼び出しなどの詳細イベントは画面へ流さず、JSONLファイルへすべて保存します。画面へ出した要約も同じファイルに保存します。既定の保存先は、実行ファイルの隣にある `flipsight/log/flipsight_<起動時刻>.jsonl` です。起動時にログファイルの絶対パスを表示します。

ログには、対局ID・盤面番号・revision・局面・残り時間、探索の開始と終了、着手・評価値・深さ・ノード数・探索時間を記録します。送信前の待機、API呼び出し、HTTP応答と通信時間、送信結果、受信通知の遅延、再接続、局面の解析エラー、対局終了も記録するため、どの段階で止まったかを確認できます。各イベントにはUTCの日時を付け、別のログ出力用スレッドで書き込み、その都度flushします。トークンとサーバーの応答本文は記録しません。

`-fslogdir`で保存先を、`-fslogfile`でファイル名を含む保存先を変更できます。両方を指定した場合は `-fslogfile` を使います。エンジン初期化時の表示と、`-noise`で有効になる探索の詳細表示は、既存の標準エラー出力へ出します。これらの表示はJSONLファイルには含まれません。

## 探索と通信

起動時には、探索用のスレッドを2M本確保します。同時対局に必要な本数が現在の確保数を超えたら、進行中の探索を止めずに増員します。必要な本数は、シンクロ対局1組につき2M本、通常対局1局につきM本です。対局が終了しても、確保したスレッドはそのまま保持します。

たとえばM=2の場合、起動時は4本です。シンクロ対局を2組同時に行うと8本になり、そこへ通常対局を1局追加すると10本になります。

シンクロ対局の2盤面の着手履歴が共通で、自分の手番が一方だけの場合は、その探索に2Mスレッドを割り当てます。着手履歴が分かれた場合や、両方が自分の手番の場合は、各盤面にMスレッドずつ割り当てて探索・ponderを行います。通常対局にはMスレッドを割り当てます。ほかの対局が増えても、この割り当ては維持します。

置換表は、通常対局なら1局の終了時、シンクロ対局なら両盤面の終了時に、対局単位で1回老化させます。同じ終了通知を再受信しても重複して老化させません。局面・評価値・着手のキャッシュを保持したまま、登録情報の重要度を下げます。老化は別のワーカーで実行し、ほかの対局の探索と通信を継続します。FlipSightモードでは、置換表の登録数に応じた自動老化の代わりに、この対局終了時の老化を使います。

レベル0〜10を指定した場合は、今後の着手と通信に必要な時間が残っていると見込めるときだけ、探索開始から送信まで最低1秒空けます。待機中も他の盤面の探索と送信は進みます。また、この起動プロセスのAPIリクエストを最小300ms間隔・直近60秒で200件以内に抑えます。HTTP 429の待機期限も、同じプロセス内で共有します。

状態の取得には認証付きイベントストリームだけを使います。`hello` で時計の基準と自分のIDを受け取り、`state` で進行中・承認待ちの対局全体を同期します。以後は `match` で更新された対局を置き換えます。古い `state.revision` は破棄し、人との対局は `room_created_at`、`round_no`、revisionの順に新旧を比較して、古い更新を破棄します。再接続時の `state` に含まれない対局は終了扱いにして探索を停止します。

接続が切れたとき、15秒間イベントが届かないとき、不正な応答などで状態の同期を維持できないときは再接続します。再接続に失敗するたびに待機を1秒から最大30秒まで延ばします。`ping` も通信の継続確認に使います。送信結果が不明な場合は、ストリームの更新または再接続後の `state` で同じ手番・revision・局面であることを確認してから、計算済みの同じ手を再送します。反則として拒否された手は、そのrevisionでは再送しません。

環境情報は起動時に `agent_environment` で一度だけ報告します。報告するのはエンジン名、OS、`-fsthread` の値、ハッシュ容量（MB）、先読みの設定、練習中ではないことを示す `practice: false` です。トークンとサーバーの応答本文はログに出力しません。Windowsでは届いたバイト数を確認してから読み、通知をバッファが埋まるまで待たせずに処理します。

## オフラインテスト

```powershell
cmake -S . -B build/flipsight -DINCLUDE_FLIPSIGHT=ON -DBUILD_FLIPSIGHT_TESTS=ON
cmake --build build/flipsight --config Release
ctest --test-dir build/flipsight -C Release --output-on-failure
```

通信形式、局面と時計、同時探索、ponder、送信結果が不明な場合の再送、送信間隔、ログの保存と画面表示を検証します。また、実エンジンのレベル10で2盤面を最後まで進め、自動パスと終了済み盤面を含む局面更新や着手送信を確認します。Windowsでは、接続を開いたまま小さな通知を送るローカル通信テストで、受信の即時性も検証します。実エンジンのテストには `bin/resources/eval.egev2` と `bin/resources/eval_move_ordering_end.egev` が必要です。テストはFlipSightへ接続しません。

API v2の初回同期、ストリームからの申し込み承諾、再接続後の同期、同じ着手の再送、古いrevisionの破棄、環境報告が一度だけ行われること、無通信時の接続キャンセルも検証します。

参考: [issue #667](https://github.com/Nyanyan/Egaroucid/issues/667)、[公式API仕様](https://othelloclub.com/ja/flipsight/lab/api#beginner)。通信の復旧処理は、指定された `FlipSight_Bot` の実装も参考にしています。
